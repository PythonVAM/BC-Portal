The four dimensions

1. SET Area

A top-level branch of the cost-centre tree. There are five SET area types:

  • R&D Division (7000) — clinical research and drug development cost centres.
  • Commercial (6200) — sales and marketing cost centres.
  • Digital & Tech (5000) — IT cost centres.
  • Corporate (1000) — finance, HR, central functions.
  • Operations (2000) — supply chain, logistics, etc.

SET Area is inferred from the cost centre's position in the hierarchy — it is the code of the top-level node under which the CC sits.

2. BC Department

An attribute on each CC indicating which boundary-change discipline it belongs to. Possible values:

  • R&D
  • SMM (Sales, Marketing & Medical)
  • G&A (General & Administrative)

Note: BC Department is independent of SET Area. For example, a CC could sit under the R&D SET area (7000) yet have a BC Department of SMM — the SET area governs what the cost can be split by, while the BC dept governs how it is classified in the boundary change submission.

3. CC selection mode

Each CC in a Cost Out submission is added as either:

  • Full CC — the entire cost centre transfers. Every GL account, every detail row at default values. The user does not enter values for this CC.
  • Partial CC — only selected GL accounts (and within those, only selected detail rows) transfer. The user enters / edits values to specify the partial amount.

4. GL category (within R&D paths)

For R&D cost centres specifically, the GL account drives a further breakdown when entering detail. 5110-STAFF and similar STAFF-flavoured GLs split by Project × Utilisation View (UV). Non-staff GLs (e.g. 6110-TRAV, 7110-CLIN) still split by Project × UV in this prototype, but in the production system they may stay at GL level only. This is a design decision worth re-confirming with the finance team.

Per-path narratives

Each path below describes the full Cost Out flow for a meaningful combination of dimensions.

R&D Division R&D Partial e.g. 7300RND-CC-041 Clinical Trials — Partial transfer ▼

Screens shown

  1. Cost centres — user adds the CC and marks it Partial.
  2. Cost out — Select — CC appears in the R&D block; user ticks the GL accounts to transfer.
  3. Cost out — Detail — every ticked GL explodes into rows by Project × UV. User can edit values, add ad-hoc rows, remove rows, copy rows.
  4. FTEs out — user enters FTE counts by location × worker type for this CC.
  5. Review & submit — includes the UV FTEs out block (since this is R&D), allocating total FTEs across Project × UV by 5110-STAFF cost weights.

Data shape

Detail rows carry: cc, gl, gln, bcDept, project, projectName, uv, fy25[12], fy26[12], fy27, fy28, fy29. The taCode/taName attribute follows the Project's Therapy Area.

Key rules

  • Every row visible on the Detail screen is part of the submission — tick-state is for toolbar action selection only.
  • The submission cannot proceed if any picked CC has zero rows remaining.
  • UV FTE allocation uses 5110-STAFF cost weights specifically. Non-staff GL costs do not enter the FTE allocation formula.
R&D Division R&D Full R&D CC, Full transfer ▼

Screens shown

  1. Cost centres — user adds the CC and marks it Full.
  2. Cost out — Select — the CC appears with all GLs pre-ticked and locked. User cannot untick.
  3. Cost out — Detail — skipped. Full CCs flow through with all backend rows at default values.
  4. FTEs out — FTE rows are auto-populated; the user cannot edit individual rows (read-only for Full CCs).
  5. Review & submit — includes UV FTEs out block with the same allocation logic.

Key rules

  • Full CCs cannot have their detail edited — the user is committing to transfer everything.
  • If a contributor's only CC is Full, they skip the Detail screen entirely.
  • A mixed submission (some Full + some Partial) still shows the Detail screen, but Full CCs do not appear there.
Commercial SMM Partial e.g. 6200COM-CC-115 Brand Marketing — Partial transfer ▼

Screens shown

  1. Cost centres — user adds the CC and marks it Partial.
  2. Cost out — Select — CC appears in the SMM block; user ticks the GL accounts.
  3. Cost out — Detail — every ticked GL explodes by Product. User can edit values, add/copy/remove rows.
  4. FTEs out — FTE rows by location × worker type.
  5. Review & submit — no UV FTEs block (SMM CCs do not need UV allocation).

Data shape

Detail rows carry: cc, gl, gln, bcDept, product, productName, isNonBrand, taCode, taName, fy25[12], fy26[12], fy27, fy28, fy29. There is no project or uv field for SMM rows.

Key rules

  • Non-brand products are flagged with a "Non Brand" pill in identity columns.
  • Same gating as R&D: every visible row is part of the submission; every CC must have at least one row.
Digital & Tech R&D Partial e.g. 5110 Platform Engineering — Partial transfer ▼

Screens shown

  1. Cost centres — user adds the CC and marks it Partial.
  2. Cost out — Select — CC appears in its own block (GL only); user ticks GL accounts.
  3. Cost out — Detail — flat list of GL rows, no further split. User edits values directly.
  4. FTEs out — FTE rows by location × worker type.
  5. Review & submit — no UV FTEs block (not R&D SET area).

Data shape

Detail rows carry: cc, gl, gln, bcDept, fy25[12], fy26[12], fy27, fy28, fy29. No product, project, UV or TA fields.

Notes

All non-R&D, non-SMM-Commercial paths (Corporate, Operations, IT, and Commercial-non-SMM) follow this same gl-only shape. The differences are cosmetic (which block-header colour, which department chip), not structural.

Cross-cutting rules (apply to all paths) ▼

Currency

  • Values are stored in USD. The Local toggle on each screen converts the displayed values using the per-CC currency from ccAttr[code].cur. Editing is only available in USD; Local mode disables inputs to prevent accidental conversion-edits.

Multi-contributor submissions

  • Multiple Cost Out Contributors may be assigned to a single BC. In the prototype, any contributor may pick any CC. In production, each contributor would be gated by their SET area.
  • If two contributors pick the same CC, last-writer-wins.

Navigation

  • Forward navigation always takes priority — "Back" preserves edits, but if the user unticks a GL on Select and then re-ticks it, the corresponding Detail rows are wiped.

Submission gates

  • Select screen: at least one GL must be ticked across the submission.
  • Detail screen: every Partial CC with picked GLs must have at least one detail row remaining.
  • FTEs out: no minimum — a CC may transfer 0 FTEs (cost-only transfer).

UV FTEs out (R&D only)

  • Visible on Review only if the submission contains at least one R&D SET area CC.
  • Allocation formula per CC, per FY: UV_FTE = total_CC_FTE × (uv_staff_cost / total_staff_cost), where staff cost is filtered to 5110-STAFF only.
  • Rows allocated to 1 decimal place, with round-and-balance so each column sums exactly to the CC's total FTE for that FY.
  • If a period has FTEs > 0 but no STAFF cost rows, the allocation is shown as — (cannot allocate).

Open questions & design notes

  • Non-staff R&D GLs — should non-staff costs (travel, contractor fees, etc.) really split by Project × UV in the production system, or only by Project? The prototype currently splits all R&D GLs by Project × UV.
  • UV FTE allocation basis — we use 5110-STAFF only. If a project has Bonus & Incentives (5210) or Contractor fees (5310) but no Salaries, that cost should arguably enter the headcount weighting too. Discuss with finance team.
  • Currency edit-back — should we allow editing in Local currency with auto-conversion back to USD? Trade-off: more flexibility vs. risk of rounding mismatch on round-trip.
  • SET area enforcement — in production, should contributors be hard-gated to their own SET area, or just defaulted?
